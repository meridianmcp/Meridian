# Meridian storage and bounded file-inspector contract

**Status:** planner decision record / implementation contract  
**Date:** 2026-08-31  
**Scope:** `meridian-build`, `meridian-outputs`, and the local-first launch wave

## Decision in one sentence

Meridian should not add a generic NoSQL database. It should use a tiered evidence
model: Postgres stores the authoritative, small metadata and lineage graph;
Tigris/S3 stores optional large immutable payloads; local disk stores working
files, offline ledgers, and rebuildable indexes; Redis remains ephemeral.

The file feature should be a **bounded file-shape inspector**, not a second
parser/index/database. It returns a deterministic, capped description of one
file and can feed `meridian-outputs` without requiring the tunnel.

## Current repository facts

| Area | Current implementation | Consequence |
|---|---|---|
| Small artifact blobs | `meridian/artifact_store.py` stores content-addressed, redacted local blobs and JSON sidecars | Useful offline baseline; not yet a hosted artifact authority |
| Output indexing | `extensions/meridian-outputs/meridian_outputs/outputs_local.py` and `meridian/outputs_indexer.py` use local DuckDB/FTS-style indexes | Fast and local; indexes must remain rebuildable |
| Output provenance | `annotate.py`, `provenance.py`, `provenance_status.py`, and `research_evidence.py` maintain local ledgers/envelopes | Stronger than a plain Markdown log, but not yet durable in hosted Postgres |
| Remote object store | `meridian/object_store.py` has an explicit inactive Tigris/S3 stub; default backend is local | Tigris credentials alone do not activate a production path |
| Sync state | `meridian/db/object_sync_state.py` is preparatory local/queued/synced/failed state | Missing durable outbox semantics, leases, retries, tombstones, and idempotency |
| Document parsing | `meridian-docs` already owns DOCX/OOXML parsing and equation handling | The generic inspector must delegate DOCX rather than re-parse it |

## Storage placement contract

### Postgres: authority and queryable control-plane metadata

Store only small, durable records needed to answer “what is this, who owns it,
what produced it, and is it trustworthy?”:

- tenant/project/run/attempt/artifact identifiers;
- content hash, byte size, media type, logical format, and schema version;
- parent/input/output lineage edges and generator/tool/script identity;
- parser version, result hash, bounded inspection summary, and acceptance state;
- permission scope, retention class, deletion/tombstone state;
- object-store key, sync state, ETag/version, retry/outbox identifiers;
- compact run-manifest and provenance-envelope JSON where it is bounded and
  indexed deliberately.

Do not place raw output bytes, full logs, previews, arbitrary user documents, or
unbounded JSON blobs in ordinary rows. Use typed columns for frequently queried
fields and bounded JSONB only for versioned, validated summaries. Postgres is the
lineage authority even when an object is temporarily local-only or remote sync
is unavailable.

### Tigris/S3: optional immutable payload tier

Use remote object storage for large, immutable or infrequently queried payloads:

- binary outputs and input snapshots when the user opted into remote retention;
- DOCX/ZIP/PDF/PNG/Parquet and large CSV/XLSX files;
- compressed evidence bundles and export packages;
- optionally, encrypted raw logs after retention policy permits them.

Keys must be generated by the server from tenant/project/run/artifact identity;
clients never choose arbitrary cross-tenant keys. The object is addressed by a
content hash or immutable version. Postgres records the object key and hash;
Tigris/S3 is never the only copy of provenance metadata and never the source of
truth for access policy.

The first hosted implementation needs an outbox row, lease, retry/backoff,
idempotency key, dead-letter state, deletion tombstone, integrity check, and
reconciliation scan. A failed upload must leave a visible `local_only` or
`sync_pending` state, never disappear and never block unrelated local work.

### Local disk: working set and offline durability

Keep these local:

- user-selected working inputs/outputs and temporary/prestage files;
- offline provenance/event ledgers and receipts;
- DuckDB/Tantivy/FTS indexes and parser caches;
- local run manifests before optional remote reconciliation.

Local indexes and caches are accelerators, not authority. Every local record
needs a portable project/run/artifact reference and source hash so it can be
reindexed or reconciled later. OneDrive is not a staging database and must not
be used for temporary generated files.

### Redis: ephemeral acceleration only

Redis may hold cache entries, short-lived locks, deduplication keys, rate-limit
counters, and queue hints. It must not be the only copy of provenance, lineage,
artifact identity, or completion state. The DB-first/write-through boundary
already exists and should be preserved.

## Bounded file-shape inspector

### Scope and delegation

The inspector is one local MCP capability with a stable response schema:

- raw XML: secure streaming parse and bounded structural summary;
- JSON: bounded structural summary and capped preview using the existing DuckDB
  JSON path where it is appropriate;
- CSV: schema/sample/row-estimate summary using DuckDB's CSV reader;
- XLSX: `.xlsx` sheet/schema/sample summary using DuckDB's Excel extension;
- XLS/XLSB/ODS: optional read-only `fastexcel`/Calamine backend only when a
  benchmark proves format coverage is required;
- DOCX/OOXML: delegate to `meridian-docs`; do not independently parse the ZIP;
- output indexing/search: continue through `meridian-outputs`, not the inspector.

“NoSQL” is a misleading name: this is a read-only inspection facade over files,
with bounded output and deterministic hashes. It does not become another store.

### Common preflight limits

Every format uses the same preflight and result envelope:

- allowlisted root and symlink/junction escape prevention;
- extension plus magic/signature check, never extension alone;
- maximum source bytes, decompressed bytes, nesting depth, node/cell/row count,
  preview size, wall-clock time, and memory budget;
- no writes, no network access, no implicit indexing, and no secret-file reads;
- cancellation and partial-result behavior for large or malformed inputs;
- stable error codes (`unsupported`, `limit_exceeded`, `malformed`, `denied`,
  `timeout`, `partial`) rather than an exception-only API.

XML must reject DTDs, entities, external resources, network access, and unsafe
XInclude/XSLT behavior. Use secure `lxml` configuration or `defusedxml` plus
explicit size/depth/time limits. ZIP-backed formats must also enforce archive
member and expansion limits.

### Canonical response

The inspector returns a validated object containing at least:

```json
{
  "inspection_id": "portable-id",
  "source_ref": "redacted-portable-reference",
  "format": "xml|json|csv|xlsx|...",
  "mime": "...",
  "size_bytes": 0,
  "source_sha256": "...",
  "parser_id": "duckdb-json|duckdb-csv|duckdb-excel|lxml-xml|...",
  "parser_version": "...",
  "result_hash": "...",
  "state": "complete|partial|failed",
  "shape": {},
  "bounds": {},
  "warnings": [],
  "errors": [],
  "provenance_ref": "project/run/artifact reference"
}
```

Volatile timestamps and machine-local absolute paths are excluded from
`result_hash`. Counts must distinguish exact values from estimates or lower
bounds. A partial result is useful but must never be presented as complete.

## Engine choices and reuse

1. **DuckDB first for JSON, CSV, and `.xlsx`.** It is already a project
   dependency, already powers recursive Outputs indexing, and avoids adding a
   second general-purpose tabular stack. Use projection, schema inspection,
   sampling, and bounded scans rather than materializing entire files.
2. **Calamine/fastexcel as an opt-in compatibility adapter.** Polars documents
   `fastexcel`/Calamine as its fast Excel reader; Calamine is read-only and
   covers legacy/modern spreadsheet formats. Do not add it to the base install
   until an XLS/XLSB/ODS corpus demonstrates that DuckDB's `.xlsx` path is
   insufficient.
3. **Secure lxml/defusedxml for raw XML.** Reuse the existing lxml dependency,
   but centralize secure parser construction and limits. Do not use this path
   for DOCX internals; `meridian-docs` owns OOXML semantics.
4. **Existing Outputs fingerprint/provenance functions remain the integration
   point.** The inspector should produce a bounded summary and source/result
   hashes that `file_fingerprint`, `tag_output`, `bind_artifact_provenance`,
   and `research_evidence` can consume.

## Implementation waves

### Wave 0 — contract and safe local capability

- implement the common response/limit/error contract;
- add raw XML and JSON inspection with security tests;
- add no new remote dependency and no tunnel requirement;
- document local-only behavior and redacted portable references.

Primary existing item: `LOCAL-FILE-INSPECTION` (`2ffd763d-9d1d-4928-82f7-ff4fb67a5113`).

### Wave 1 — tabular adapters

- reuse DuckDB for bounded CSV/JSON/XLSX shape inspection;
- add deterministic sample/schema/result hashing;
- benchmark memory and latency on small, large, malformed, and adversarial
  files;
- add Calamine/fastexcel only if compatibility results justify it.

Planned item: `LOCAL-FILE-INSPECTION-TABULAR` in the launch-readiness group.

### Wave 2 — provenance binding

- make the run manifest the portable unit connecting project, run, input,
  output, inspector/parser, hashes, and receipts;
- keep local ledgers usable offline and reconcile them to Postgres metadata;
- record failures and partial states explicitly;
- avoid copying raw payloads into Postgres.

Primary existing item: `LAUNCH-OUTPUTS` (`37ce5537-e603-44b1-b66e-3c3d3369a435`),
alongside the existing canonical-provenance work.

### Wave 3 — optional remote payloads

- implement Tigris/S3 only behind an explicit capability flag;
- add tenant-scoped keys, quotas, retention, outbox/lease/retry,
  reconciliation, deletion tombstones, and integrity verification;
- run a small pilot before making remote storage the hosted default.

Primary existing items: `TIGRIS-AUTHZ-PLAN`, `TIGRIS-AUTHZ-IMPLEMENT`, and the
manual inactive-bucket setup gate.

## Manual decisions still required

- choose remote-retention defaults and per-plan quotas;
- decide whether raw inputs, raw outputs, logs, or only export bundles are
  eligible for remote retention;
- approve the Tigris/S3 pilot and supply credentials through the secret manager;
- rotate any credential-bearing local MCP snippets before public rollout;
- choose a representative CSV/JSON/XML/XLSX benchmark corpus.

No Tigris activation is required to implement or use the local inspector or
local Outputs provenance. The Tigris bucket may remain provisioned but inactive.

## Acceptance gate

This work is ready for hosted use only when a fresh local session can inspect a
single file without a tunnel, return a deterministic bounded result, bind it to
a run/artifact reference, and survive malformed/oversized/partial input without
losing the provenance record. Remote storage is an additive optimization and
must pass tenant-isolation, retry/reconciliation, deletion, and integrity tests
before activation.

## Research basis

- DuckDB's official extension docs cover built-in JSON and Excel support and
  the `.xlsx` boundary.
- Polars' official Excel guide identifies `fastexcel` as its fast reader path.
- Calamine is a read-only Rust reader covering xls/xlsx/xlsm/xlsb/xla/xlam/ods.
- `defusedxml` documents the DTD/entity/external-resource threat model and the
  need for explicit resource limits.
